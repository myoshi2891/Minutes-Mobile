# 実機試験の記録

シミュレータで再現できない試験（[../01-requirements/test-requirements.md](../01-requirements/test-requirements.md) §3.7 の TST-DEV 群など）の結果を置く。様式と置き場所は [../03-detailed-design/dev-environment.md](../03-detailed-design/dev-environment.md) §15 で決めた。

## 1. 規則

- 試験 1 回を 1 行で、`device-tests.md`（最初の記録のときに作る）の表に追記する。行は消さず、やり直した場合は新しい行を足す。
- **録音データそのものは置かない。** 置くのは §2 の様式の項目（日付・ビルドのコミット・端末機種・OS 版・試験 ID・結果・観測値（件数・ハッシュを含む）・不合格の理由）だけで、音声とその書き起こしの本文は置かない（SEC-SUP-04・05）。実機で録音した音声を、記録・Issue・PR に貼らない。
- 自動の検査（`scripts/check.sh`）が通ったことと、実機試験が済んだことは別に扱う。実機試験が必要な要件は、この記録に「合格」があるか、「未実施」の行に理由と実施予定が書いてあるときに完了とする（[test-requirements.md](../01-requirements/test-requirements.md) §6 の 4）。「未実施」は実機での合格ではないので、実施したら結果の行を足す。
- **実施した試験は、実機の試験も含めてすべて合格していることを完了の条件にする**（[test-requirements.md](../01-requirements/test-requirements.md) §6 の 1）。試験 ID ごとに最新の結果の行で判定し、最新が「不合格」か「判定不能」なら完了にしない。**「未実施」の行は試験の結果ではない**ので、判定に使う最新の結果の行として数えない。同じ試験 ID の前の「不合格」・「判定不能」の後に「未実施」の行を足しても、その不合格・判定不能は解消せず、完了にしない（未実施の行で完了にできるのは、その試験 ID に実施した結果の行がない場合と、最新の実施した結果が「合格」の場合だけ）。前の不合格の行は消さずに残す。後で同じ試験 ID を再試験して合格した場合は、その合格の行が前の不合格に代わる（前の不合格は完了を妨げない）。ただし、再試験は不合格の原因を直したビルドで行い（原因がビルドにないと判断した場合はその理由を書く）、**不合格になったときと同じ端末機種・OS 版で行う**（別の端末・OS 版での合格は、その不合格に代わらない。別の条件の合格の行は残すが、前の不合格は解消しない）。合格の行の観測値に、代わる不合格の行の日付を書く。
- **シミュレータで通ったことを実機の合格として扱わない。** シミュレータの結果をこの記録の「合格」に書かない。
- Personal Team の署名は約 7 日で失効する（CON-02）。試験の前にビルドを入れ直す。

## 2. 様式

| 列 | 内容 |
| --- | --- |
| 日付 | 試験した日（`YYYY-MM-DD`） |
| ビルドのコミット | 試験したビルドのコミットのハッシュ |
| 端末機種 | 例: iPhone の機種名 |
| OS 版 | 例: iOS 27.2 |
| 試験 ID | 例: TST-DEV-01 |
| 結果 | 合格・不合格・未実施・判定不能 |
| 観測値 | Chunk 数・空白区間・電池・温度など、試験の合格条件が求める値（TST-DEV-03 ではロック・解除の時刻とロック区間のサンプル数、試験音の再生を始めた時刻・周波数・長さと、見つかった区間のサンプル番号、⑥の合図の間隔・番号の付け方・再生を始めた時刻と終えた時刻、見つからなかった・重複した番号と、隣り合う合図の間隔の差の最大（その番号とサンプル番号）、TST-DEV-01 ⑥（TST-DEV-03 で割り込みを起こした場合も同じ）では割り込みごとの種類・独立に測った開始と終了の時刻と、対応づけた空白区間の開始と終了との差（境界ごと）を含む） |
| 不合格の理由 | 不合格・未実施・判定不能のときに書く。未実施なら実施の予定も書く |
