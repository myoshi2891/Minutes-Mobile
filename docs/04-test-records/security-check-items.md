## 1. 位置づけ

| 知りたいこと | 正 |

| 試験の種類ごとの項目（結合・E2E・実機） | [integration-test-items.md](integration-test-items.md)・[e2e-test-items.md](e2e-test-items.md)・[device-test-design.md](device-test-design.md) |
| 観点ごとの確認項目・手段・時期と、SEC・脅威・NS 番号からの逆引き | 本書 |

- 既存の 3 つの項目書は試験の種類で切ってある。本書は、同じ項目を「守る対象と脅威」で切り直す索引である。項目は作り直さず、番号（`IT-…`・`E2E-…`・`DV-…`）で引く。
- **1 項目は「1 つの観点を 1 つの手段で確かめる」単位**である。同じ観点を自動の検査と実機の両方で確かめる場合は、行を分ける（手段の偏りを §5 で見るため）。
- 合格条件・規則の本文は写さない。確認項目の文は本書の言葉での要約で、「正」の列の記述と食い違ったら、正に従って本書を直す。
- **番号**（`SCI-<領域>-nn`）は作業用で、要件 ID ではない（[../README.md](../README.md) §3 の体系には入れない）。
- **区分**: 「定義済み」は TST か設計書に出典がある。「候補（既出）」は、ほかの項目書がすでに候補として載せているもの。「候補（新規）」は本書で初めて挙げるもので、出典がない（§7）。採用するときは、スキル `update-specs` の手順で TST・規則・詳細設計の一覧に足してから、区分を書き換える。
- **状態と結果は本書に持たない。** 結果が残る場所は §3 にある。

## 3. 確認手段と結果の置き場所

「手段」の列に書く言葉と、実行するもの・時期・結果が残る場所。

| 手段 | 実行するもの | 時期 | 結果が残る場所 |

| 秘密情報 | 手順 3（gitleaks の全履歴とステージした差分、録音データの混入の検査 `check-tracked-files.py`） | コミット前・プッシュ前 | 同上 |
| 版の照合 | 手順 0（`setup-tools.sh --verify`） | プッシュ前 | 同上 |
| 自己試験 | `test-lint-rules.py`・`test-checks.py`（手順 0・2〜5・10 の中で回る） | プッシュ前 | 同上 |
| ビルド | 手順 6。型やターゲットの依存で「書けない」ようにしてある項目 | プッシュ前 | 同上 |
| 単体・結合 | 手順 7（Swift Testing） | プッシュ前 | 詳細設計の「要件 ID ↔ テストの対応表」の状態 |
| UI | 手順 9（XCUITest） | PR の作成前 | 同上 |
| 実機 | 個人の iPhone を人が操作する | 機能の完成時とリリース前 | [README.md](README.md) の様式で作る `device-tests.md` |
| レビュー | PR のチェックリスト（[security-requirements.md](../01-requirements/security-requirements.md) §10.2）と、各設計書の NS 番号 | PR ごと | PR の説明 |
| 運用 | 実機試験と記録の扱い | そのつど | 残さない（守る規則である） |

- 「前提」の列は、その確認を始められる作業を [PROGRESS.md](../../PROGRESS.md) §1 の「順」の番号で書く（3 プロジェクト設定・4 共通基盤・5 録音・6 保存・7 確定・8 復旧・9 文字起こし・10 画面・11 書き出し）。「済」は作業単位 1 で入れてあり、今も実行されている検査である。
- 設定の検査は検査の側（自己試験）が通っているが、実物の `project.xcproj` は作業単位 2 の変更の後に通る。Git のフックも作業単位 2 の最後に有効にする（[dev-environment.md](../03-detailed-design/dev-environment.md) §4.1・§5）。
- 自動の検査が通ったことと、実機の確認が済んだことは別に扱う（[test-requirements.md](../01-requirements/test-requirements.md) §6）。

## 8. 残る危険と、対象外にしているもの

確認しても塞げないもの、設計で「対象外」「制御の外」と決めたものを集める。ここに挙げたものは、項目を足しても合格にできない。扱いを変えるときは、要件（SEC）の側を変える。

| 事項 | 扱い | 出典 |
| --- | --- | --- |
| タイトルの入力欄で、OS 標準の編集メニューから利用者がコピーした場合は、端末内限定と有効期限が付かない | 残る危険として記録する（利用者自身の操作による） | SEC-PLT-01、ui.md §7.3 |

| 改ざん検知・脱獄検知をしない | 対象外（P3 で再評価） | SEC-SUP-06 |
| アプリ独自の暗号化をしない。保存データは端末のファイル保護で守るので、パスコードを設定していない端末では保護クラスが効かない | MVP では行わない（P2 で再評価）。実機試験はパスコードを設定した端末で行う | SEC-DAT-08、device-test-design.md §3.1 |
| 録音中に書くファイルと、全会議で共有する DB は、ロック中も書ける保護クラスのままである（最初のロック解除の後は、ロック中も読める） | 設計上の選択。D1・D2 を共有の DB に置かないことと、未完了の作業がなくなった会議を保管へ切り替えることで範囲を狭める | SEC-DAT-01・02、storage.md §11、BD-ARC-03 |
