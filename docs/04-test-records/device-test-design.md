| 項目 | 内容 |
| --- | --- |
| 版 | 0.1（土台。アプリの実装前） |

プログラムによる試験（単体・結合・UI）では確かめられず、個人の iPhone を人が操作して確かめる試験について、観点・機材・試験ケースの骨子をまとめる。

**本書は土台である。** アプリは未実装なので、画面の文言・ボタンの名前・秒数などの手順の細部は書いていない。細部は、各作業単位の実装の後に本書へ足す（§11）。

## 1. 位置づけ

| 知りたいこと | 正 |
| --- | --- |
| 合格条件（何を満たせば合格か） | [test-requirements.md](../01-requirements/test-requirements.md) §3（TST の表） |
| 観点・機材・手順の骨子・実施の順序 | 本書 |
| 試験の結果（1 回 1 行） | [README.md](README.md) の様式に従う `device-tests.md`（最初の記録のときに作る） |

- 自動で実行する試験の項目は、[integration-test-items.md](integration-test-items.md)（機能・結合）と [e2e-test-items.md](e2e-test-items.md)（E2E）にある。E2E のうち、差し替えのない実機の通しは本書が正である（同書 §4 に対応表がある）。
- 合格条件は本書に写さない（写すと食い違うため）。本書は「何を見るか（確認観点）」と「何を記録するか（観測値）」を書く。
- 本書の観点番号（`DV-<領域>-nn`）は、観点を指すための作業用の番号である。要件 ID ではない（[../README.md](../README.md) §3 の体系には入れない）。
- TST に定義のない観点は「候補」として載せる（§7）。採用するときは、スキル `update-specs` の手順で test-requirements.md に TST を足してから、本書の区分を「定義済み」に書き換える。

## 2. 対象の判定基準

次のどれかに当たるものを、本書の対象にする。観点の表（§5）の「理由」の列に、この記号を書く。

| 記号 | プログラムで確かめられない理由 | 例 |
| --- | --- | --- |
| A | OS の資源管理に依存する（画面ロック・背面・サスペンド・継続処理タスク・強制終了） | 60 分の録音、ロック中の文字起こし |
| B | ハードウェアと音声の経路に依存する | 着信、Siri、Bluetooth、実際のマイク |
| C | OS のデータ保護・セキュリティ機能に依存する | 保護クラス、バックアップ、スナップショット、キーボード |
| D | 実際の音声認識エンジンと OS のアセットに依存する | 日本語の認識、言語アセットの取得 |
| E | ほかのアプリ・ほかの機器との受け渡しである | 共有シート、AirDrop、Windows での展開 |
| F | 人の知覚と判断が要る | VoiceOver、文言、スクロールの滑らかさ |
| G | 保証せずに実測して記録する値である | 電池、温度、実時間比、開始までの時間 |
| H | 配布と運用の手順である | 署名の失効、上書きでの導入、アプリの削除 |

対象にしないもの:

- 依存を差し替えれば再現できる事象（状態遷移・ファイルの破損・空き容量の値など）。単体・結合テストで扱う（TST-GEN-04）。
- 自動テストを実機の上で実行するだけのもの。ただし、実機で実行すること自体が要求されているものは、観点の表に載せる（TST-AUD-02）。

## 3. 試験環境と準備

### 3.1 端末とビルド

| 項目 | 条件 |
| --- | --- |
| 端末 | 個人の iPhone（UD-02）。機種名と OS の版を記録に書く |
| パスコード | 設定する（保護クラスはパスコードがないと効かない。TST-DEV-03） |
| ビルド | Personal Team の署名。試験したビルドのコミットのハッシュを記録に書く |
| 入れ直し | 署名は約 7 日で失効する（CON-02）。試験の前にビルドを入れ直す |
| Bundle Identifier | 確定した値のビルドで行う。確定するまで、実機で実際の会議を録音しない（CON-09、BD-DEV-06） |

### 3.2 補助の機材

| 機材 | 使う試験 |
| --- | --- |
| 試験音を再生する別の端末（周波数と長さが既知の正弦波） | TST-DEV-01 |
| 着信をかけるための別の電話 | TST-DEV-02 |
| Bluetooth の入力機器（AirPods など） | TST-DEV-04 |
| Mac（Finder でのバックアップと復元、コンソールでのログの確認、書き出したファイルの解析） | TST-DEV-01・08、DV-SEC-06 |
| サードパーティー製キーボード（無償のもの） | TST-SEC-10 |
| Windows の PC | DV-EXP-04（候補） |
| 同じ Apple Account の別の端末 | DV-SEC-05（候補） |

機材とアプリは無償のものに限る。費用が発生しうるものは、オーナーの確認が記録されるまで使わない（UD-05）。

### 3.3 してはいけないこと

- 実際の会議を録音しない。試験の音声は、試験音（正弦波・無音・雑音）と端末内の音声合成に限る（TST-GEN-08）。人が読み上げた声も録音の試験に使わない。
- 録音データ（音声）と、文字起こしの本文・テキストを、記録・Issue・PR に貼らない（SEC-SUP-04・05）。合格条件が求める観測値（件数・結果・ハッシュ・時刻・試験音の周波数と長さ・サンプル番号・空白区間の長さ・電池と温度など。[test-requirements.md](../01-requirements/test-requirements.md) §3.7 の試験記録の様式と [README.md](README.md) §2）は記録してよい。
- iCloud のバックアップを使わない（容量の費用が生じうる。TST-DEV-08）。
- 残したい録音がある端末で、端末の内容を置き換える試験（TST-DEV-08）と、容量を埋める試験（TST-DEV-06）を行わない。先に書き出す。

## 4. 観測手段

手動の試験は、合格条件が求める値を**実機から読める**ことが前提になる。読む手段が設計書に決まっていないものを、ここで明らかにする。

| 観測値 | 使う試験 | 読む手段の候補 | 状態 |
| --- | --- | --- | --- |
| Chunk の数・連番・SHA-256 | TST-DEV-01・03・05・08 | 書き出したアーカイブの目録（`ExportManifest`。[export.md](../03-detailed-design/export.md) §4.2）と、同梱の Chunk を Mac で照合する | 目録の項目は設計済み。照合の手順とスクリプトは未作成 |
| 総サンプル数 | TST-DEV-01 | 書き出した Chunk の大きさから Mac で数える | 未作成 |
| 空白区間・入力経路の変更・停止理由 | TST-DEV-02・04・05 | 目録、会議の詳細の画面 | 画面に出す範囲は実装後に確かめる |
| 試験音の周波数の成分 | TST-DEV-01 | 書き出した WAV の該当区間（サンプル番号で特定）を Mac で解析する | 解析の方法とスクリプトは未作成 |
| 計測値（開始までの時間・あふれの回数・時計とサンプル数の差・割り込みの回数・電池残量・温度状態。[recording.md](../03-detailed-design/recording.md) §8） | TST-DEV-01・02 | `usage_metrics`（SQLite） | **未確定。** 記録する設計はあるが、実機で値を読む手段（画面・書き出し）が設計書にない |
| 文字起こしの実時間比・信頼度 | TST-STT-07 | 同上 | **未確定**（同上） |
| ファイルの保護クラスの属性 | TST-DEV-03・10 | アプリが属性を読み戻した結果（[storage.md](../03-detailed-design/storage.md) §12.4） | **未確定。** 読み戻した結果を人が見る手段が設計書にない |
| 保存ルートの下のファイルの有無 | TST-DEV-08、DV-EXP-01 | — | **未確定。** 「アプリが空の状態で起動する」ことは画面で分かるが、ファイルが 1 つもないことを確かめる手段が設計書にない |
| 電池の残量 | TST-DEV-01 | OS の設定アプリで、開始時と終了時に読む | 手順を実装後に確定する |
| 本アプリの通信先 | TST-DEV-07 | OS の「App プライバシーレポート」（TST-SEC-02） | 手順を実装後に確定する |
| ログの内容 | DV-SEC-06 | Mac のコンソール（[architecture.md](../03-detailed-design/architecture.md) §13.2） | 手順を実装後に確定する |

「未確定」の 4 件は、該当する作業単位の詳細設計を再確認するとき（[詳細設計 README](../03-detailed-design/README.md) §2）に、手段を決めて設計書へ足す。決めるときの条件:

- 観測のための出力に、D1〜D3（音声・本文・タイトル）を含めない（SEC-LOG-03、SEC-PLT-07）。
- 観測のためだけの通信を足さない（SEC-NET-01）。
- 試験用の入口を Release のビルドに残さない（起動の引数と同じ扱い。[dev-environment.md](../03-detailed-design/dev-environment.md) §13）。

## 5. テスト観点の一覧

列の意味:

- **TST**: 合格条件の正。かっこの中は、同じ条件を単体・結合で確かめている TST。
- **前提**: 試験の前に実装が済んでいる必要のある作業（[PROGRESS.md](../../PROGRESS.md) §1 の「順」の番号。5 録音・6 保存・7 確定・8 復旧・9 文字起こし・10 画面・11 書き出し）。
- **区分**: 「定義済み」は TST に合格条件がある。「候補」は TST がなく、採否が決まっていない（§7）。

出典の文書名は、断りがなければ詳細設計（`docs/03-detailed-design/`）である。

## 6. 試験ケースの骨子

定義済みの試験だけを書く。候補は、採用が決まってから足す。

各ケースの「操作の骨子」は順序だけを示す。画面の名前・ボタン・待つ時間は、実装の後に確定して書き足す。合格条件は、見出しの TST の行（[test-requirements.md](../01-requirements/test-requirements.md) §3）を正とする。

### TST-DEV-01 60 分の連続録音

- **観点**: DV-REC-01〜06
- **前提と機材**: 書き出しの実装（11）の後に行う（観測値を書き出したアーカイブと WAV から読む。§4・§8）。電池の残量が十分にある。充電器を外す（電池消費を測るため）。試験音を再生する別の端末
- **操作の骨子**:
  1. 電池の残量を記録し、録音を始める
  2. 開始の直後に試験音を入れる
  3. 画面をロックし、ロック中に試験音を入れる
  4. 解除してほかのアプリに切り替え、その間に試験音を入れる
  5. 本アプリに戻る。経過時間が 60 分を過ぎたことを確かめてから試験音を入れ、その後に停止して確定する（停止は 60 分を過ぎてからだけ行う。試験音は停止の直前の区間に入る）
  6. 電池の残量を記録し、録音を書き出して Mac で照合する
- **確認観点**: a 連番とハッシュ ／ b 総サンプル数 ／ c 時計との差と空白区間 ／ d 試験音の 4 区間 ／ e あふれの回数 ／ f 電池と温度
- **観測値**: Chunk の数、総サンプル数、時計との差、空白区間（区間と理由）、あふれの回数、電池の残量（開始・終了）、温度状態の推移、試験音の区間ごとの成分
- **結果で見直す設計**: リングバッファの容量と合図の周期、追記と同期の方式（[recording.md](../03-detailed-design/recording.md) §14、[storage.md](../03-detailed-design/storage.md) §15）、時計との差の上限（初期値 1 秒）
- **中止と後片付け**: 端末が高温の警告を出したら中止する。試験の会議は、記録を取った後に削除する

### TST-DEV-02 録音中の割り込み

- **観点**: DV-INT-01〜09
- **前提と機材**: 着信をかける別の電話。アラームを数分後に設定しておく
- **操作の骨子**: 録音を始め、割り込みを 1 種類ずつ起こす。割り込みごとに、録音の状態（画面と通知）と、終わった後に再開したかを確かめる。最後に停止して確定する
- **確認観点**: a 着信に出て、すぐ切る ／ b 着信に出て、数分後に切る（空白の長さ）／ c 着信に出ない ／ d Siri ／ e アラーム ／ f 再開が許されない場合の表示 ／ g 予約通知 ／ h 停止の後の OS の録音インジケータ
- **観測値**: 割り込みごとの、届いた通知の順序と内容、空白区間の長さと理由、再開の成否、割り込みの回数
- **結果で見直す設計**: 予約通知までの時間（初期値 60 秒）、通知が届かない場合の再開の方法（[recording.md](../03-detailed-design/recording.md) §14）、OQ-01 の結論
- **中止と後片付け**: 試験の会議を削除する。アラームを解除する

### TST-DEV-03 画面ロック中の録音とファイル保護

- **観点**: DV-STO-01〜05
- **前提と機材**: 書き出しの実装（11）の後に行う（Chunk の数を書き出したアーカイブから読む。§4・§8）。パスコードを設定した端末
- **操作の骨子**:

  4. 別の回として、確定の後に保管への切り替えが済む前にロックした場合と、端末を再起動した直後の動作を確かめる
- **確認観点**: a ロック中の Chunk の保存 ／ b 属性（処理中・保管後）／ c ロック中の新しいファイルへの属性の付与 ／ d 保管への切り替えの保留と解消 ／ e 再起動の直後の起動
- **観測値**: ロック中に保存された Chunk の数、属性の値、切り替えの保留の有無

- **中止と後片付け**: 試験の会議を削除する

- **確認観点**: a 開始の前の表示 ／ b 録音中の警告 ／ c 最上位の警告 ／ d 書き込みの失敗の表示と保持の件数 ／ e 上限での停止と停止理由
- **観測値**: 段階ごとの空き容量と表示、保持した Chunk の数、停止理由

### TST-DEV-08 バックアップからの除外

- **観点**: DV-STO-09
- **前提と機材**: Mac。残したいデータのない端末（復元は端末の内容を置き換える）
- **操作の骨子**: 合格条件の「方法」の①〜③のとおりに行う（試験用の会議を作る → Finder でバックアップ → 復元して同じ Bundle Identifier のビルドを入れ直す）
- **確認観点**: a 会議が 1 件も戻らない ／ b 判定の対象のファイルがない ／ c 対照の設定値が戻っている（戻っていなければ「判定不能」）
- **観測値**: 復元の前の会議の数・Chunk の数・ハッシュ、復元の後の会議の数、対照の設定値
- **中止と後片付け**: 端末を元の状態へ戻す手順を、始める前に用意する
- **先に決めること**: 保存ルートの下のファイルの有無を確かめる手段（§4）
- **順序**: 端末の内容を置き換えるので、ほかの試験の後に行う（§8）

### TST-DEV-10 ロック中のバックグラウンド文字起こし

- **観点**: DV-STT-05
- **前提と機材**: パスコードを設定した端末。言語アセットを取得済み。自動の文字起こしを有効にする
- **操作の骨子**: 数分の録音を停止して確定し、直後に画面をロックする。しばらく待って解除し、文字起こしがどこまで進んだかを確かめる
- **確認観点**: a ロック中に進む、または延期されて再開する ／ b 読み書きが保護クラスで失敗しない
- **観測値**: ロック中に完了した Chunk の数、延期・失敗の記録
- **結果で見直す設計**: OQ-10、保護クラスを切り替える時点（[storage.md](../03-detailed-design/storage.md) §8）

### TST-DEV-11 継続処理タスクでの文字起こし

- **観点**: DV-STT-06〜09
- **前提と機材**: Personal Team のビルド。言語アセットを取得済み
- **操作の骨子**: 文字起こしを前面で始め、アプリを背面に回し、画面をロックする。しばらく待って前面に戻す
- **確認観点**: a 投入の成否と進行表示 ／ b 進行表示の内容 ／ c 背面・ロック中の進み方 ／ d 打ち切りの後の再開と重複 ／ e 投入できない場合の代替
- **観測値**: 投入の成否、背面で完了した Chunk の数、打ち切りの有無、重複セグメントの数、どちらの方式で判定したか
- **結果で見直す設計**: OQ-03、背景モードの設定、進捗の報告の間隔（[transcription.md](../03-detailed-design/transcription.md) §14）

### TST-DEV-12 Live Activity

- **観点**: DV-UI-01〜04、DV-INT-08
- **前提と機材**: Personal Team のビルド
- **操作の骨子**: 録音を始めて画面をロックし、ロック画面とダイナミックアイランドの表示を確かめる。割り込みを起こして表示の変化を確かめ、停止して表示が終わることを確かめる
- **確認観点**: a 状態と経過時間の表示 ／ b 中断中への変化 ／ c 停止での終了 ／ d 予約通知 ／ e タイトル・本文が出ない ／ f 使えない場合の代替の条件
- **観測値**: 表示の有無、更新の遅れ、どちらの方式で判定したか
- **結果で見直す設計**: OQ-04、BD-UI-03（[ui.md](../03-detailed-design/ui.md) §14）

## 8. 実施の時期と順序

実機試験は「機能の完成時」と「リリース前」に行う（[test-requirements.md](../01-requirements/test-requirements.md) §1.1）。

| 時期（[PROGRESS.md](../../PROGRESS.md) §1 の順） | 行える試験 |
| --- | --- |
| 録音〜復旧の実装の後（5〜8） | TST-DEV-02・04、TST-AUD-02 の実機での実行 |
| 文字起こしの実装の後（9） | TST-STT-07、TST-DEV-10・11 |
| 画面の実装の後（10） | TST-DEV-12、TST-SEC-09・10、TST-DEV-06 |

| リリース前 | 定義済みの全件をやり直す。採用した候補を行う |

- **画面より前の試験の操作手段は未確定である。** 録音〜文字起こし（5〜9）の実装が済んでも、画面（10）がなければ実機で録音を始められない。作業単位ごとに実機で確かめるなら、仮の操作手段が要る。画面の実装まで待つなら、上の表の最初の 2 行は 10 の後になる。どちらにするかは、録音の実装の着手時に決める（§11）。

## 9. 合否と記録

- 結果は「合格・不合格・未実施・判定不能」のどれかで、[README.md](README.md) の様式で 1 回 1 行を記録する。確認観点（a、b、…）ごとの結果は、観測値の列に書く。
- 確認観点が 1 つでも不合格なら、その試験は不合格である。
- 実機試験が必要な要件は、記録に「合格」があるか、「未実施」の行に理由と実施予定が書いてあるときに完了になる（[test-requirements.md](../01-requirements/test-requirements.md) §6 の 1・4、[README.md](README.md) §1）。実施した試験には合格を求める。「未実施」の行は試験の結果ではないので、同じ試験 ID の前の「不合格」・「判定不能」を解消しない（解消するのは、その後の「合格」の行だけ）。
- 試験の結果で設計を確定・見直すものは、同じ作業で設計書へ戻す。

## 10. セキュリティとプライバシーの注意

- 試験で作った録音・文字起こし・書き出したファイルは、記録を取った後に端末と Mac から削除する。リポジトリに入れない（SEC-SUP-04・05）。
- 記録・Issue・PR に貼る画面の写真に、会議タイトル・本文が写らないようにする。
- 観測のための手段（§4）は、音声・本文・タイトルを外へ出さない形にする。
- 着信の試験で使う電話番号などの個人の情報を、記録に書かない。
